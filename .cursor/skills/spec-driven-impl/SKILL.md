# 先规格再实现（SDD + TDD 链路）

## 为什么需要

M3 修补任务的最大教训：**功能元素清单 ≠ 可实现的设计**。用户列出"功能点 + 操作逻辑"后，若直接跳到改代码，会反复撞"图与真实执行相反""点选无法回写""从此处运行语义不清"这类问题。真正可动手的标志是**执行时序对齐**——用户原话："功能元素使用逻辑确认完成，相当于确认执行的时序图，可以开始修改代码了"。

本 skill 把"从需求到代码"的链路显式化，每一步都有产物与验收，Agent 不再凭感觉跳步。

## 链路（不可跳序）

1. **需求冻结**：用户给出功能元素 + 操作逻辑 + 补充优先级（冲突以补充为准）。Agent 产出一份**确认稿**回读给用户，列出功能元素、操作逻辑、已删除/降级的点（如版本管理删除、CFG 统一展示）。
2. **时序对齐**：把每个功能点展开为"用户操作 → 系统响应 → 数据流转"的时序。**只有时序对齐，才算设计确认**。静态结构图不够。用可视化原型（HTML/Figma）让用户肉眼验证时序，比文字更难误读。
3. **差距分析**：对照确认稿与时序，逐条比对现有代码，产出三段：
   - **A 缺陷清单**：每条带"现象 / 根因 / 涉及文件 / 与 spec 哪条冲突"。按严重度排序（图与执行相反 > 交互缺失 > 字段缺失）。
   - **B 实施计划**：把缺陷归并为可独立交付的子任务（B1/B2/…），每个子任务自带测试清单与验收点。子任务粒度 = 一个 worktree 能在一个回合内完成并自验。
   - **C 风险与决策点**：列出会破坏既有契约的改动（schema 变更、协议变更、测试与新 spec 冲突），**必须显式问用户**，不要默默决定。
4. **决策点确认**：对 C 中的每条，用 AskQuestion 让用户拍板。典型需确认的：schema 字段增减、跨层签名变更、旧测试能否改/删。其余用合理默认，但在报告里标注"默认决定"。
5. **测试先行**：每个 B 子任务先写 `test/` 骨架或 `docs/plan/plan.md` 验收清单，再写实现。文档也走测试先行——先写验收清单再改 spec。
6. **三方一致**：同一概念在多处出现时（如控制流组在 CFG 图/执行器/编辑器三处），三处必须可证明一致。用穷尽性 `switch` + `assertNever` 强制编译期覆盖，不写运行时兜底——新类型漏处理要编译报错，不能静默错渲。
7. **边界兜底**：跨 WS/JSON/CDP 边界，`undefined` 经序列化变 `null`，函数默认参数对 `null` 失效。一律 `x = x ?? {}`，不依赖默认参数；接收方 `sanitize` 把 `null` 还原 `undefined`。
8. **可运行性 + 性能**：编译/单测全绿不等于真机不崩。Mock 过的路径要真机或近真机跑一次（见 `runtime-runnability-review`）。性能优化必须先有测试守住功能，再降阶。

## 产物清单（每个子任务合并前必须存在）

- `docs/design/visual-mask-ui-spec.md` 对应小节已更新（设计先行）。
- `docs/plan/plan.md` 有该子任务的验收清单（测试先行）。
- `test/<feature>.test.ts` 全绿，且 UI 主链路走 `test/ui-core-e2e.test.ts` 的 `app.boot()` + `[data-action]` 点击，禁止只用内部 API 直调冒充用户路径。
- `docs/architecture/architecture.md` 同步 schema/协议变更（架构有变必须同步，否则 code-review 不通过）。
- 三角色跑过：`test-first-dev` / `code-review-standard` / `runtime-runnability-review`。

## 反模式（直接打回）

- **跳过时序对齐**：只确认功能清单就改代码 → 必然返工。
- **默默改 schema/协议**：`control.name`、`playback(script, fromStepId)` 这类契约变更不问用户 → 破坏既有约束。
- **为让实现过而改测试断言**：除非确认是 spec 纠正导致旧测试失效（且经用户确认可改/删），否则禁止。
- **图/执行/编辑三方之一漏处理新类型**：用 `default:` 当顺序组处理 → 新类型静默错渲。
- **跨边界用默认参数兜底**：`null` 进来默认参数不触发 → 真机崩，Mock 绿。
- **视图态污染数据态**：折叠/缩放/选中态写进 `Step`/`Script` → 不可变约定破，撤销/版本错乱。

## 与其他 skill 的关系

- `test-first-dev`：本 skill 第 5 步的具体执行。
- `code-review-standard`：本 skill 第 6 步三方一致 + 产物清单的审查方。
- `runtime-runnability-review`：本 skill第 7、8 步的审查方。
- `worktree-dev`：本 skill 第 3 步子任务粒度的物理隔离手段。
