
# 一、产品定位与目标

## 1.1 一句话定位

面向 **Electron 桌面客户端** 的「可录制、可生成、可润色、可在版本更新后自动执行」的测试/操作自动化平台：底层用 CDP 控制应用，对外以 **Skill + MCP** 提供能力，支持 ==**Agent 驱动**== 与 ==**脚本回放**== 双模式，并在两者之间可互相转换。

## 1.2 目标

|目标|说明|
|---|---|
|G1 可控执行|能对指定 Electron 客户端执行完整操作流程（点击、输入、等待、断言等）|
|G2 更新可触发|客户端版本更新后，能自动拉起一次执行（Agent 任务或脚本）|
|G3 理解可辅助|支持 Agent 基于页面结构分析可交互元素与流程，降低从零编写成本|
|G4 人工可润色|Agent 产出或录制结果可导入为步骤序列，人工增删改后再固化|
|G5 双模互通|Agent 现场执行 ↔ 导出脚本 ↔ MCP 导入执行/再编辑|

## 1.3 非目标（本期不做或弱化）

- 不保证对任意原生非 Chromium 控件 100% 覆盖（系统文件框、托盘、部分原生菜单需降级方案）
- 不承诺「零人工、全自动适应任意大改版」
- 不做通用 RPA 替代所有桌面软件（聚焦 Electron + CDP 可达部分）

## 1.4 角色

|角色|职责|
|---|---|
|测试/自动化工程师|配置目标应用、录制/润色步骤、配置断言与更新触发|
|Agent（系统内）|分析页面、生成/执行操作、导出步骤脚本|
|运维/定时系统|监听版本变更，触发 Agent 任务或脚本任务|
|管理员|权限、调试端口策略、环境与密钥|

# 二、需求用例详述

用例编号：UC-xx。每条含：触发、前置、主成功路径、扩展/异常、后置。

---

### UC-01 连接目标 Electron 客户端

**作为** 工程师/Agent **我想要** 通过 CDP 连接到目标客户端 **以便** 后续录制、分析或执行操作

**前置**：客户端支持或可开启 --remote-debugging-port；本机网络/防火墙允许本地端口。

**主成功路径**：

1. 用户指定应用路径或「附着已运行进程 + 端口」。
2. 系统启动应用（可选带调试端口）或连接已有端口。
3. 列举 window/context，选中主操作目标。
4. 返回连接成功与基本窗口信息。

**异常**：端口占用、生产包禁用调试、多实例冲突 → 明确错误码与处理建议。

**后置**：会话可被后续 Tool 复用。

---

### UC-02 分析页面可交互元素（覆盖性）

**作为** Agent/工程师 **我想要** 得到当前界面可交互元素清单及结构 **以便** 理解能点什么、填什么，评估覆盖是否完整

**主成功路径**：

1. 对当前目标做 Accessibility/DOM 快照。
2. 输出可交互节点（role、name、状态、大致位置/层级）。
3. （可选）按区域/业务分组（导航、表单、主操作、弹层）。
4. （可选）标记「疑似阻断」元素（模态、引导、权限墙）。

**扩展**：多窗口/多 webview 分别快照并汇总。

**异常**：快照过大 → 分页/裁剪/按可见区域；跨域 webview 权限不足 → 降级提示。

**验收关注点**：不是保证「业务语义 100% 懂」，而是**结构可交互集合可枚举、可复查**。

---

### UC-03 Agent 现场执行一套操作任务

**作为** 用户/调度系统 **我想要** 用自然语言或任务描述让 Agent 操作客户端 **以便** 完成一次探索、回归或临时任务

**主成功路径**：

1. 创建任务（目标描述、是否允许破坏性操作、超时）。
2. Agent 循环：快照 → 决策 → 调用 MCP Tool 操作 → 再观察。
3. 达到结束条件或用户停止。
4. 产出执行日志、截图、步骤轨迹。

**异常**：某步失败可重试/换策略；超时终止并保留现场快照。

**后置**：轨迹可进入「导出脚本」（UC-07）。

---

### UC-04 版本更新后自动触发执行

**作为** 调度系统 **我想要** 在客户端版本变化时自动跑一次任务 **以便** 无需人工盯更新

**前置**：已配置「监听对象」（安装目录/可执行文件/版本号来源）与「触发动作」（脚本 ID 或 Agent 任务模板）。

**主成功路径**：

1. 监听版本号或关键文件变更（含防抖，避免更新过程中多次触发）。
2. 确认更新结束（进程退出再拉起 / 版本号稳定 / 可选健康检查）。
3. 按策略启动：
    - **模式 A**：执行已发布脚本（确定性）；
    - **模式 B**：创建 Agent 任务（模板 + 当前版本元数据）；
    - **模式 C**：先脚本，失败再升级为 Agent 修复/重跑。
4. 记录触发原因、版本号、结果。

**异常**：更新中文件抖动、启动失败、调试端口未就绪 → 重试与退避。

**说明（回应你的顾虑）**： Agent 模式与脚本模式一样可以被「版本变更事件」触发；差异在于任务入口是「Agent 任务模板 ID」，而不是「脚本文件路径」。

---

### UC-05 手动录制操作序列

**作为** 工程师 **我想要** 通过真实点击/输入把操作记成步骤 **以便** 不依赖自然语言描述每一步

**主成功路径**：

1. 进入录制态（连接已建立）。
2. 用户在客户端中操作；系统记录为结构化步骤（定位尽量语义化）。
3. 控制台展示步骤列表；可对目标窗口高亮最近一步。
4. 结束录制，得到可编辑序列。

**扩展**：「蒙版/序号」展示历史点击；点选某步修改（UC-08）。

**异常**：定位过脆 → 提示改为 role/text/testid；原生控件未录入 → 标记需手工补全。

---

### UC-06 配置步骤的期望结果（断言）

**作为** 工程师 **我想要** 为某步或整段流程配置可选期望结果 **以便** 判断是否真正成功，而不只是「没报错」

**主成功路径**：

1. 选择步骤或流程级断言。
2. 配置类型：元素存在/可见、文案包含、URL/标题、截图对比、自定义表达式等。
3. 执行时断言失败则流程失败并保留现场。

**扩展**：用于发现「新增阻断」（有弹层未处理导致最终状态不对）。

---

### UC-07 Agent 执行后导出脚本

**作为** 用户 **我想要** 把 Agent 的操作轨迹导出为可导入脚本 **以便** 后续不反复现场推理，或先固化再润色

**主成功路径**：

1. 从一次 Agent 运行取步骤轨迹。
2. 转换为与 MCP 一致的步骤模型（含定位、输入、等待、断言占位）。
3. 导出文件或写入脚本库。
4. 可用 MCP「导入脚本」加载。

**验收**：导出脚本可不经过 Agent、仅靠执行器跑通同一主路径（允许少量手工润色）。

---

### UC-08 导入脚本并润色操作序列

**作为** 工程师 **我想要** 导入脚本后增删改某一步 **以便** 在 Agent 结果上做最小人工校正

**主成功路径**：

1. 导入脚本。
2. 列表展示步骤；支持插入、删除、调整顺序、改定位/参数/断言。
3. （可选）单步试跑、从某步继续跑。
4. 保存为新版本脚本。

**扩展**：与录制高亮联动，选中步骤时在客户端高亮对应元素。

---

### UC-09 执行已润色脚本（确定性回放）

**作为** 调度/工程师 **我想要** 直接执行脚本 **以便** 稳定、可重复、低成本回归

**主成功路径**：连接 → 按序执行 → 断言 → 报告。 **异常**：失败时输出失败步骤、快照、与上次成功基准的 Diff 入口（为后续修复准备）。

---

### UC-10 失败后的辅助修复（可选增强）

**作为** 工程师 **我想要** 在脚本失败时获得最小修改建议 **以便** 降低「每次用自然语言重述整页」的成本

**主成功路径**：

1. 失败自动采集当前快照。
2. 与成功基准 Diff（含新增可交互元素）。
3. Agent/规则给出补丁（改选择器或插入步骤）。
4. 人工确认后合并。

**说明**：不替代 UC-08，而是减少描述工作量。

---

### UC-11 评估「交互覆盖是否完整」（针对你的顾虑）

**作为** 工程师/Agent **我想要** 知道当前分析是否可能漏掉重要可交互点 **以便** 判断能否放心让 Agent 在新版本上探索

**主成功路径**：

1. 输出可交互元素集合与可见性。
2. 对比「历史版本快照」或「脚本中曾用到的元素」。
3. 报告：新增/消失/变更的可交互项；未覆盖的可见主按钮等启发式告警。

**边界**：无法自动保证理解全部「业务逻辑」，但可保证**结构层覆盖可度量**，业务层靠断言与人工抽检。

---

### UC-12 权限与安全

连接调试端口、执行破坏性操作、导出日志需授权；生产环境默认限制自动启动带调试端口的包；敏感输入可掩码存储。

# 附录：可选插件 —— Git 式脚本版本管理

> **定位：解耦的可插拔增强项，不属于主体「生成测试脚本」流程。**
> 主体流程（录制 → 实时生成步骤 → 润色/编辑/建组 → 运行全部）**不依赖**本模块。
> 本模块以**可选插件**形态存在：保留可扩展接口（见 `src/script/version-store.ts` 的 `createStore/commit/branch/switchTo/cherryPick/tag/getHistory/getBranches/getTags/getCurrentScript/diffScripts`），UI 层通过注入式回调接入，默认不挂载、不暴露操作按钮。

**原 UC-10b 需求（保留待后续插件化实现）**

**作为** 工程师 **我想要** 像用 git 管理代码一样管理脚本步骤 **以便** 在尝试不同步骤组合、对比方案、复用他人/其他分支的好步骤时，不丢历史、可回滚、可迁移

**核心模型**：
- 每一个 **最外层顺序组（Sequential Group）** = 当前分支上的一次 **commit**（版本快照）。选择组/循环组不是切出点（§2.3.0 控制流约束）。
- 一个 Script = 一条分支链；整个脚本库 = 一个仓库（多脚本 = 多分支集合）。
- CFG 表达组内/组间控制结构，Git 表达组级版本演进与跨脚本复用；history 视图为二者融合图。

**功能清单（git 思想适配，砍 reset/merge/rebase）**：
| git 概念 | 脚本映射 | 交互 |
|---|---|---|
| commit | 每次生成/修改最外层顺序组 = 一次提交（不可变） | 自动产生，不覆盖历史 |
| branch | 从某最外层顺序组切出新分支 | 选中该组→「从此组开分支」；选择/循环组内不可切 |
| switch | 切换分支查看不同步骤版本 | 分支列表→切换→CFG 视图渲染该分支 |
| cherry-pick | 跨分支搬运组（含内部结构） | 他分支选组→pick→作为当前分支新提交追加（可改参再落） |
| history | 提交关系图（融合 CFG） | 节点=顺序组、结构边=控制流；多分支叠加分叉 |
| tag | 标记某版本为基线 | 分支某点打 tag（如「v1 通过版」） |
| diff | 组/步级差异 | 选两组→显示字段差异（locator/value/kind/结构） |

**实现约束（插件化）**：
1. 版本状态在 UI 侧/本地（`UiShell` 持有 store），`UiKernel` 不上提版本（DIP）。
2. UI 入口（提交/分支/tag/cherry-pick）须为可插拔：默认隐藏，挂载开关由宿主配置决定。
3. `src/script/version-store.ts` 保持纯函数、不可变 API，作为插件唯一数据真相源；`src/ui/version-panel.ts` 保持 SRP 渲染组件，仅消费 store + 回调。
4. 接入时不破坏主体流程：主体流程的「增删改/运行」不因版本插件存在与否而改变行为。

**关联**：设计落点见 `docs/design/visual-mask-ui-spec.md §6`；实现前须更新本附录与架构文档（CODEBUDDY.md §5.1/§5.2）。

## 模型视觉断言

断言方法可配置为：**把截图 + 提示词交给模型，由模型判断该断言是否成立**。

- 与现有 `exists` / `textContains` **并列**，作为断言 `kind` 的扩展点（OCP：新增一种判定策略，不改执行器调度）。
- 入参是「当前截图（或元素截图）」和「用户/脚本写的提示词」；出参是通过 / 不通过（可带简短理由）。
- **不写死供应商 API**：不在需求里绑定某一家模型、某一个 HTTP 接口或某一个 SDK。接入时由宿主注入「可调用的判定函数」或配置端点，内核只依赖「截图 + 提示词 → 是否成立」这层契约。
- 适用场景举例：现有 DOM 快照扫不到的视觉差异、弹层文案因截断/虚拟列表不稳定时的人工级判断。不替代 `textContains`「点击后是否弹出含指定文字的组件」这一主路径。
- 实现前须：冻结断言 kind 名与脚本 JSON 字段（C 类决策点，须显式问用户）、补 `test/` 骨架、同步 `docs/design/design.md` 与架构文档。在那之前禁止把模型调用写进 `src/executor/assert.ts`。
