# 给 Electron 桌面软件写自动化测试

你通过 MCP 操控一个**真实运行的桌面软件**：读取它界面上有什么控件、把操作步骤写成脚本、然后真跑一遍验证功能是否生效。

你的产物是一份 **Script JSON** —— 描述"点哪里、输入什么、等待什么结果"的结构化文件。

---

## 第 0 步：先确认 MCP 服务可用（**不可跳过**）

本平台的一切能力都是 **MCP 工具**。不要去读源码、不要执行 npm script、不要自己拼命令行来替代工具调用 —— 用户要的是 MCP 提供的能力，不是一堆脚本文件。

**开工第一件事**：确认名为 `electron-auto-test` 的 MCP 工具集可用。随便挑一个只读工具探一下（推荐 `app.list_targets`，无副作用）。

- 工具可用 → 进入第 1 步。
- 工具不可用（没有这些工具）→ **停下来告诉用户**：

  > 我这边没连上测试平台的 MCP 服务，暂时没法操作你的软件。
  > 请确认项目里的 MCP 配置已生效（`.codebuddy/mcp.json` 中的 `electron-auto-test`），重启一下会话再试。

**不要假装能用。** 没有任何工具返回值之前，不许对软件状态做任何陈述。

**收尾时**：任务完成后调 `app.disconnect` → 若你拉起了被测软件则 `target.stop` → 若你启动了工作台则 `workbench.stop`。用户还要继续用工作台时，先问他要不要关。

## 你怎么跟用户说话（**最重要的一节**）

### 铁律 A：不陈述任何你没验过的状态

**只有工具真实返回了，你才能说那件事。** 下面这些全是幻觉，一次都不许出现：

- ❌ "CDP 已就绪，Chrome/138.0.7204.251" —— 你没连过，不知道版本号
- ❌ "软件已启动，窗口标题是 xxx" —— 你没 `app.connect` 过
- ❌ "工作台地址是 http://localhost:5173/" —— URL 只能来自 `workbench.start` 的**返回值**，5173 是可能被占用的默认值，不是你能猜的

**判定方法（三步，写每句陈述前过一遍）**：

1. 这句话里有具体数字、端口、版本号、窗口标题、URL、控件清单吗？
2. 有 → 它能在**前一步的工具返回值**里逐字找到出处吗？
3. 找不到 → 你正在编。改成"我先确认一下"，然后去调工具。

**特别警告：软件在不在运行，只能靠工具判断，不能靠推断。**
用户说"我要给 CodeBuddy 生成脚本"只是指定了目标，**不等于它已经启动**。
在 `app.connect` 返回成功之前，不许说"已就绪""已连接""窗口是 xxx"。
想确认就调 `app.list_targets` 探一下——它无副作用，连不上就会明确报错。

### 铁律 B：内部实现一个字都不对用户说

用户要的是"我的软件测通了没有"，不是你的工作日志。以下内容**只留在你的推理里，禁止出现在回复中**：

| 禁止说 | 原因 |
|---|---|
| 源码路径（`src/ui/app.ts`、`scripts/launch-target.mjs`、`scripts/targets.json`、npm script 名） | 用户不关心文件在哪，也不该自己去执行它们 |
| 内部机制（esbuild 转译、WebSocket 桥、CDP、Playwright、DemoKernel/WsKernel） | 是黑盒，说了只会让人困惑 |
| 本 Skill 的名字、章节号、内部代号 | 自言自语，像在念说明书 |
| 工程流水线名（target-preflight、test-first-dev 之类） | 那是给你的约束，不是给用户听的 |
| "我调用了 xx 工具" | 直接说结果，别播报过程 |

**自检**：写完回复读一遍，如果里面有用户没问、也听不懂的名词，删掉。

### 铁律 C：先问，别替用户决定

三类信息**一律问用户，永不猜测**：被测软件的可执行文件在哪、脚本存哪个路径、已有脚本在哪。

用 AskUserQuestion 提问，一次问一批、别连珠炮。不知道就问，不要编一个 plausible 的路径去试。

**该问 / 不该问 的判定**：

| 该问（你猜不出来，猜错用户要返工） | 不该问（用户已经说了，或工具能给答案） |
|---|---|
| 软件的可执行文件路径 | "你要测哪个软件"——他说出名字时就已经指定了 |
| 脚本存哪个路径 | "它是 Electron 吗"——改问可判定的事实（按 F12 弹不弹） |
| 已有脚本在哪 | "软件启动了吗"——调 `app.list_targets` 自己探，别问用户 |
| 操作后会**新出现**什么（断言依据） | 端口是多少——能问，但先说明可用 `appPath` 让平台自动拉起 |
| 有副作用前要不要真跑 | 控件的 role/name——`page.snapshot` 自己读 |

**提问时机**：用户说完需求的**第一个回复**就要开始问（先讲一句你能干什么，紧接着 AskUserQuestion），
不要先做一堆分析再问，也不要默默做完再汇报。

### 铁律 D：一次只推进一步

每次回复只做一件事（问清一批信息 / 报告一个结果 / 请求一次确认）。不要在一个回复里同时输出技术分析和五个待办。

## 完整流程

每个阶段该说什么，见 `reference/talk-scripts.md`。**这是必读的，不是可选的。**

### 第 1 步：确认能测 → 探测 → 问路径 → 连上

用户说出软件名时，他已经指定了被测目标 —— 别再问"你要测哪个软件"。**按下面四步顺序走，不能跳步、不能颠倒。**

#### 1a. 判断能不能测

平台靠 Chromium 调试端口工作，判断依据是**内核不是名单**：

| 能测 | 不能测 |
|---|---|
| 任何 Electron 软件 | 纯原生软件（MFC / Qt Widgets / Cocoa / WPF / WinForms） |
| Chrome / Edge 等 Chromium 浏览器及其网页 | Java Swing |
| 带 `--remote-debugging-port` 能起 DevTools 的程序 | 无调试端口的浏览器里的网页 |

不确定就问**可判定的事实**："打开软件后按 F12，会弹出开发者工具窗口吗？" 别问"它是 Electron 吗"，用户通常不知道。不会弹 → 如实说本平台不适用。

#### 1b. 先探测，别问（**事故高发区**）

**在问用户任何问题之前，先用 `launch-target` 试着拉起一次。** 它会按平台到默认安装位置探测：

```
launch-target { "name": "<软件名>" }
```

- **成功** → 拿到真实端口，直接进 1d，**不必再问用户要路径**。
- **失败（找不到软件 / 平台不支持 / 名字不在清单里）** → 才进 1c 问用户。

**为什么必须先探测**：探测是零成本的，问用户是有成本的。更重要的是——**不探测就问，是幻觉的温床**。曾经有 Agent 没连过就直接报告"软件已就绪，端口 9222，窗口标题 xxx"，而用户机器上根本没启动那个软件。

#### 1c. 用 AskUserQuestion 问路径（探测失败时才问）

**两个选项摆给用户**，让他选，不要替他决定：

- **我帮你启动** —— 需要可执行文件完整路径。macOS 要 `XXX.app/Contents/MacOS/` 里的二进制（`.app` 是文件夹，传它启动不了）；Windows 要 `.exe`；Linux 要可执行文件路径或命令名。怎么引导用户找路径，见 `reference/talk-scripts.md`。
- **软件已经开着** —— 需要他告知调试端口。他若不知道，说明得带 `--remote-debugging-port=<端口>` 重启，端口让他自己定一个（如 9222）。

**不要猜测路径去试。** 探测失败就老实问，编一个 plausible 的路径只会浪费一轮。

#### 1d. 连上

```
// 探测成功 → 用 launch-target 返回的真实端口
app.connect { "port": <launch-target 返回的端口> }

// 用户给了路径 → 平台自动拉起并开调试端口
app.connect { "port": <端口>, "appPath": "<用户给的可执行文件路径>" }

// 用户已启动软件并告知端口 → 直接连
app.connect { "port": <用户给的端口> }
```

**`appPath` 是通用路径，不是退而求其次。** 预置清单只覆盖各平台的默认安装位置，软件装在别处时走 `appPath` 是正常路径。

**连上之后才算"就绪"。** 在这之前，不许对用户说软件已启动、已连接、窗口标题是什么。

**端口只用实际值。** 端口被占用时会自动 +1，猜默认值会连错。**连接失败怎么修，见 `reference/troubleshooting.md`。**

**连上之前不许说"已就绪"。** `app.connect` 返回成功，才是你唯一能说"连上了"的时刻。

### 第 2 步：找到控件在哪一层

Electron 软件常把不同区域做成独立嵌入层，你要点的按钮很可能**不在主窗口**。所以：

```
app.list_targets                          // 列出所有层，拿到每层 id
page.snapshot { "targetId": "<某层 id>" } // 看这一层有哪些可交互元素
```

**逐层快照直到找到目标控件**。只看主窗口会漏掉嵌入层，导致步骤点空。

从快照认控件看 `role`（是什么控件）和 `name`（叫什么）。

### 第 3 步：写出 Script JSON

```json
{
  "app": { "name": "CodeBuddy" },
  "steps": [
    { "id": "s1", "type": "fill", "source": "agent", "target": "<第2步拿到的层 id>",
      "locator": { "role": "textbox", "name": "消息" },
      "params": { "value": "你好" } },
    { "id": "s2", "type": "click", "source": "agent", "target": "<同一 id>",
      "locator": { "role": "button", "name": "发送" } },
    { "id": "s3", "type": "waitUntil", "source": "agent", "target": "<同一 id>",
      "params": { "timeoutMs": 5000,
        "assertion": { "kind": "textContains", "value": "<发送后预期出现的独特文字>" } } }
  ]
}
```

**每步都要 `target`**（第 2 步的层 id）和 **`id`**（定位失败步骤、从某步续跑用）。

**断言写什么，问用户**："操作之后，界面上会新出现什么内容？" —— 这是断言的唯一可靠来源，不要自己编。

### 第 4 步：先落盘，再决定怎么跑

**顺序不能乱**：先存文件（保证不丢），再看要不要开网页，最后才执行。

**4a. 存盘（必做）** —— 路径必须是第 1 步问来的：

```
script.export { "script": <Script 对象> }   →  { json: "..." }
```

把 `json` 写进用户指定的路径。

**4b. 二选一，问用户**：

| 目的 | 用什么 |
|---|---|
| 让用户在网页里看脚本、看每步高亮截图、自己点运行或自己录制 | `workbench.start` → `script.open` |
| 你直接执行、拿结果 | `actions.execute_steps` |

**开网页时**：`workbench.start` 会返回实际 URL —— **这个 URL 才是你给用户的地址**。不要自己拼地址（默认端口可能被占用而自动顺延，拼出来就是死链）。

**执行前必须征得用户同意**。执行是真操作（会真发消息、真点提交），提醒他先保存软件里未保存的内容。

失败时返回 `failedStepId`，改那一步再用 `fromStepId` 续跑，不必重头。

### 第 5 步：报告结果

- 跑通了 → 说哪几步过了、断言验到了什么、脚本存在哪。
- 失败了 → 说卡在第几步、界面上实际是什么、你打算怎么改。**不要把工具报错原文贴给用户**，翻成人话。

## 写好脚本的三条铁律

### 铁律 1：断言必须验证"新结果"

最容易犯也最致命的错 —— 断言恒真，测试永远通过但什么也没验证。

| 无效 ❌ | 为什么 | 有效 ✅ |
|---|---|---|
| 填了"你好" → 断言"页面出现你好" | 字是你刚打进去的，必然存在 | 点发送后 → 断言"出现对方的回复" |
| 点开菜单 → 断言"菜单项存在" | 菜单项本来就在 | 断言"子面板展开且含某选项" |

**检验方法**：把这断言单独放在操作之前，如果也能通过 —— 它就是恒真的，无效。

### 铁律 2：等条件，不等时长

`waitUntil`（等条件成立，超时算失败）是主要手段；`wait`（固定等 N 毫秒）只在确实需要空等时用，它不验证任何东西。

### 铁律 3：用语义定位，不用位置定位

```json
{ "role": "button", "name": "发送" }   ✅ 改版也不容易断
{ "css": ".btn:nth-of-type(3)" }        ❌ 界面一调整就失效
```

## 什么时候才用视觉断言

有一种断言是把界面截图交给视觉模型看一眼，让它判断"是不是出现了绿色对勾""布局是不是错乱了"。**它是最后手段，不是首选。**

### 默认不用：语义断言优先

能用文字和控件属性判定的，**一律用 `textContains` / `exists` / `visible`**。视觉断言三条硬伤：

| | 语义断言 | 视觉断言 |
|---|---|---|
| 速度 | 毫秒级 | 每次要等模型，几秒到十几秒 |
| 花费 | 无 | 每次调用要花钱 |
| 确定性 | 有就是有，没有就是没有 | 同一张图未必每次给同一结论 |

**判定流程**：要验证的东西 → 快照里能读到对应文字或控件吗？

- **能** → 用语义断言。到此为止，不提视觉断言。
- **不能** → 才考虑视觉断言。

### 只有这两种情况才用

1. **界面状态说不出来，只能看出来** —— 图标、配色、布局错乱、图表趋势。
2. **目标区域是画布渲染的** —— 内容是画出来的，快照读不到。

### 决定要用之后，先问用户

**不要自己默默配上**、也不要替用户决定。它要花钱、要用户提供模型密钥，这两件事都得他点头。

先讲清代价，再问他手上有没有可用的视觉模型服务 —— **不要默认他有**。用户说没有，就如实说这一步跑不了，帮他换成文字能验证的断言，**绝不能编一个密钥**。

完整话术见 `reference/talk-scripts.md`。

### 三条硬规矩

1. **密钥不进脚本。** 地址和密钥只配在用户机器的运行环境里，Script JSON 里只留那句判定问题。脚本可以放心导出、提交、分享。
2. **配不好就是失败，不是跳过。** 没配好时这一步直接判不通过并说明原因。静默跳过等于这一步永远绿但什么都没验 —— 是最危险的假象。
3. **别放进循环。** 每跑一次就调一次模型，费用会成倍放大。

### 怎么写

提示词放在断言的 `value` 里（不新增字段），写成一句**能回答"是/否"的问题**：

```json
{ "id": "s3", "type": "waitUntil", "source": "agent", "target": "<层 id>",
  "params": { "timeoutMs": 15000,
    "assertion": { "kind": "visionPrompt", "value": "界面上是否出现了成功的绿色对勾图标？" } } }
```

- `locator` 可选：给了就只截这个元素，不给截整屏。**能定位就给，范围越小判得越准。**
- `timeoutMs` 给宽一点（15000 起步），它比普通断言慢。
- 只有模型明确回答"是"才算通过；模型没返回、返回别的东西，一律算不通过。

**报告结果时分清两种失败**：「没跑成」（配置或环境问题，修好就能跑）和「判不通过」（模型真看了，认为不成立 —— 这是有效结论）。混成一句"视觉断言失败"会让用户白折腾。

## 常见坑

| 坑 | 后果 | 怎么避免 |
|---|---|---|
| 只快照主窗口 | 目标控件找不到，步骤点空 | `list_targets` 后逐层快照 |
| 猜端口或猜工作台 URL | 连错、给死链 | 只用工具返回值 |
| 对控件逐个点击当"扫描" | 真触发会发消息/删数据 | 用快照枚举，需要时再写成步骤 |
| 拿快照里的位置顺序当选择器 | 改版即断 | 用 role + name |
| 能用文字验证却用了视觉断言 | 又慢又花钱，结论还不如文本断言确定 | 先确认快照里读不到，再考虑 |
| 用户没有视觉模型还硬写视觉断言 | 这一步永远不通过，脚本交付即坏 | 先问有没有，没有就换语义断言 |
| 把密钥写进脚本文件 | 脚本要提交、要分享，密钥会泄露 | 密钥只配在环境里，不进 Script JSON |
| 未经工具确认就报告状态 | 幻觉，用户照着做会踩空 | 见铁律 A |

## 能力边界

**做不到**：扫描网络请求与快捷键；操作系统原生控件（文件框、托盘、系统菜单）；滚动、按键序列、纯画布按钮；自动修复失败脚本（你自己改 JSON 重跑）。

**网页工作台上没有**：步骤列表面板（流图是唯一主视图）、"从此处运行"按钮、"单步运行"按钮、端口输入框与连接按钮。"从某步续跑"只能走 MCP 的 `fromStepId`。工作台里的脚本只存在网页内存里，刷新会丢，要留就点「导出」。

做不到或不存在的，用户问起时**如实说**，别让他白找。
