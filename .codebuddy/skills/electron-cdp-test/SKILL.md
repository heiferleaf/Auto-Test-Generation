# 给 Electron 桌面软件写自动化测试

你通过 MCP 操控一个**真实运行的桌面软件**：读取它界面上有什么控件、把操作步骤写成脚本、然后真跑一遍验证功能是否生效。

你的产物是一份 **Script JSON** —— 描述"点哪里、输入什么、等待什么结果"的结构化文件。

---

## 第 0 步：先确认 MCP 服务可用（**不可跳过**）

本平台的一切能力都是 **MCP 工具**。不要去读源码、不要执行 npm script、不要自己拼命令行来替代工具调用 —— 用户要的是 MCP 提供的能力，不是一堆脚本文件。

**开工第一件事**：确认名为 `electron-auto-test` 的 MCP 工具集可用。随便挑一个只读工具探一下（推荐 `app.list_targets`，无副作用）。

- 工具可用 → 进入第 1 步。
- 工具不可用（没有这些工具）→ **停下来告诉用户**：

  > 我这边没连上测试平台的 MCP 服务，暂时没法操作你的软件。
  > 项目里应该有个 MCP 配置（项目根目录下，文件名以点号开头、以 `.mcp.json` 结尾）。
  > 请确认它已生效，重启一下会话再试。

**不要假装能用。** 没有任何工具返回值之前，不许对软件状态做任何陈述。

**更不要用命令行替代。** MCP 工具没连上时，**绝不许**改成去执行命令行脚本（跑启动脚本、执行 npm 命令、拼 CDP 请求）。那样做等于绕开了整个平台，用户拿到的是一堆脚本文件而不是测试能力，而且你无法保证调用方式和服务端一致。**工具不可用就是不可用，如实告诉用户，让他说怎么修。**

## 收尾：什么该你关、什么让用户关

任务完成时按这个顺序收，顺序不能乱：

1. `app.disconnect` —— 断开 CDP，始终要调。
2. `target.stop` —— **只在你自己 `launch-target` 拉起了软件时调**。
3. `workbench.stop` —— **只要你开过工作台就必须调**。

两条容易搞反，逐条说清为什么：

**工作台（网页）必须你来关，别等用户说。**
它是后台 node 进程，用户看不见它、也不会想到要去关它，忘记关就一直占着端口，
下次再开还会顺延到别的端口，越积越多。所以只要是你 `workbench.start` 开的，
收工就 `workbench.stop`。只有用户明说"网页我先开着"时才留着。

> 反过来：**用户提醒你"网页没关"时，立刻 `workbench.stop`，别解释、别先去干别的。**
> 用户能注意到这件事，说明他已经看到残留实例了。

**被测软件：谁拉起谁关，用户自己开的不许动。**
用户自己在那个软件里操作、有没保存的文件，你擅自杀掉就是毁他的工作现场。
判定标准只有一条：**这次会话里你调过 `launch-target` 吗？**
调过 → `target.stop`；没调过 → 留着，最多在收尾时提醒一句
"调试用的 CodeBuddy 还开着，你不用了直接关掉就行"。

## 你怎么跟用户说话（**最重要的一节**）

### 铁律 A：不陈述任何你没验过的状态

**只有工具真实返回了，你才能说那件事。** 下面这些全是幻觉，一次都不许出现：

- ❌ "CDP 已就绪，Chrome/138.0.7204.251" —— 你没连过，不知道版本号
- ❌ "软件已启动，窗口标题是 xxx" —— 你没 `app.connect` 过
- ❌ "工作台地址是 http://localhost:5173/" —— URL 只能来自 `workbench.start` 的**返回值**，5173 是可能被占用的默认值，不是你能猜的

**判定方法（三步，写每句陈述前过一遍）**：

1. 这句话里有具体数字、端口、版本号、窗口标题、URL、控件清单吗？
2. 有 → 它能在**前一步的工具返回值**里逐字找到出处吗？
3. 找不到 → 你正在编。改成"我先确认一下"，然后去调工具。

**特别警告：软件在不在运行，只能靠工具判断，不能靠推断。**
用户说"我要给 CodeBuddy 生成脚本"只是指定了目标，**不等于它已经启动**。
在 `app.connect` 返回成功之前，不许说"已就绪""已连接""窗口是 xxx"。
想确认就调 `app.list_targets` 探一下——它无副作用，连不上就会明确报错。

### 铁律 B：内部实现一个字都不对用户说

用户要的是"我的软件测通了没有"，不是你的工作日志。以下内容**只留在你的推理里，禁止出现在回复中**：

| 禁止说 | 原因 |
|---|---|
| 源码路径（`src/ui/app.ts`、`scripts/launch-target.mjs`、`scripts/targets.json`、npm script 名） | 用户不关心文件在哪，也不该自己去执行它们 |
| 内部机制（esbuild 转译、WebSocket 桥、CDP、Playwright、DemoKernel/WsKernel） | 是黑盒，说了只会让人困惑 |
| 本 Skill 的名字、章节号、内部代号 | 自言自语，像在念说明书 |
| 工程流水线名（target-preflight、test-first-dev 之类） | 那是给你的约束，不是给用户听的 |
| "我调用了 xx 工具" | 直接说结果，别播报过程 |
| **工具返回的原始 JSON**（`{"connected":true,"port":9222}`、`{"name":"codebuddy","label":"CodeBuddy CN"}`） | 那是给你看的数据结构，不是给用户看的内容 |

**工具返回值只许"翻译"，不许"转发"。** 工具给你 JSON，你要做的是从中取出结论说给人听，不是把 JSON 原样贴出去。贴原文等于让用户自己去解析你的内部数据。

| 工具返回 | ❌ 直接贴 | ✅ 翻译成 |
|---|---|---|
| `{"connected":true,"port":9222}` | `连接成功：{"connected":true,"port":9222}` | "已经连上你的 CodeBuddy 了" |
| `{"name":"codebuddy","label":"CodeBuddy CN",...}` | 贴这串 JSON | "找到 CodeBuddy 了"（多数时候不必单独说） |
| `{"url":"http://localhost:5174/"}` | `workbench.start → {"url":...}` | "工作台开好了：http://localhost:5174/"（URL 照抄，一个字都别改） |

**唯一例外是 URL**：地址必须原样给出，让用户能直接点开或复制。除了 URL，返回值里没有用户需要逐字看到的东西。

**自检**：写完回复读一遍，如果里面有用户没问、也听不懂的名词，删掉。特别检查有没有 `{` `}` 出现在给用户的话里。

### 铁律 C：先问，别替用户决定

五类信息**一律问用户，永不猜测**：

1. **他想怎么用**（四种路径的哪一种，见第 1 步 1b）
2. **要测哪个功能 / 场景** —— "测聊天界面""测登录""测导出"这类目标
3. 被测软件的可执行文件在哪
4. 脚本存哪个路径
5. 已有脚本在哪

用 AskUserQuestion 提问，一次问一批、别连珠炮。不知道就问，不要编一个 plausible 的路径去试。

**第 2 条是最容易犯的。** 用户说"帮我测一下 CodeBuddy"，他只指定了**软件**，没有指定**测什么**。
这时候你要是自己去读界面、挑一个看起来重要的区域（聊天框、登录页、侧边栏）当目标往下做，
你就是在**替他决定产品范围** —— 他可能根本不想测那个。软件名 ≠ 测试目标，必须等他说。

**该问 / 不该问 的判定**：

| 该问（你猜不出来，猜错用户要返工） | 不该问（用户已经说了，或工具能给答案） |
|---|---|
| **他想怎么用（四种路径）** | "你要测哪个软件"——他说出名字时就已经指定了 |
| **要测哪个功能 / 场景** | "它是 Electron 吗"——改问可判定的事实（按 F12 弹不弹） |
| 软件的可执行文件路径 | "软件启动了吗"——调 `app.list_targets` 自己探，别问用户 |
| 脚本存哪个路径 | 端口是多少——能问，但先说明可用 `appPath` 让平台自动拉起 |
| 已有脚本在哪 | 控件的 role/name——`page.snapshot` 自己读 |
| 操作后会**新出现**什么（断言依据） | |
| 有副作用前要不要真跑 | |

**在他选定路径之前，不许连软件、不许拉起软件、不许探测。** 拉起软件是有副作用的动作
（会在他桌面上开一个窗口），探测也是在他没表态之前替他铺路。
正确顺序永远是：**先问清楚要干什么 → 再动手连。**
怕"没连过就瞎说"？那是铁律 A 管的（不许陈述没验过的状态），
靠"闭嘴不编"解决，不是靠"先斩后奏地连上去"解决。

**提问时机**：用户说完需求的**第一个回复**就要开始问（先讲一句你能干什么，紧接着 AskUserQuestion），
不要先做一堆分析再问，也不要默默做完再汇报。

### 铁律 D：一次只推进一步

每次回复只做一件事（问清一批信息 / 报告一个结果 / 请求一次确认）。不要在一个回复里同时输出技术分析和五个待办。

## 完整流程

每个阶段该说什么，见 `reference/talk-scripts.md`。**这是必读的，不是可选的。**

### 第 1 步：确认能测 → 问他想怎么用 → 连上 → 告诉他能做什么

用户说出软件名时，他已经指定了被测目标 —— 别再问"你要测哪个软件"。
但**软件名不等于测试目标**，测哪个功能还得他亲口说（铁律 C 第 2 条）。
**按下面顺序走，不能跳步、不能颠倒。**

#### 1a. 判断能不能测

平台靠 Chromium 调试端口工作，判断依据是**内核不是名单**：

| 能测 | 不能测 |
|---|---|
| 任何 Electron 软件 | 纯原生软件（MFC / Qt Widgets / Cocoa / WPF / WinForms） |
| Chrome / Edge 等 Chromium 浏览器及其网页 | Java Swing |
| 带 `--remote-debugging-port` 能起 DevTools 的程序 | 无调试端口的浏览器里的网页 |

不确定就问**可判定的事实**："打开软件后按 F12，会弹出开发者工具窗口吗？" 别问"它是 Electron 吗"，用户通常不知道。不会弹 → 如实说本平台不适用。

#### 1b. 先问他想怎么用（**在连软件之前，不可跳过**）

四种路径摆给他选。**不要替他挑，也不要因为"他大概想要脚本"就默认第一种。**

| 路径 | 他想要什么 | 你接下来做什么 |
|---|---|---|
| **A. 我帮你写，你来确认** | 一份能跑的脚本 | 连上 → 读控件 → 写脚本 → 问他验证依据 → 存盘 → 征得同意后执行 |
| **B. 开网页，我自己构建** | 自己录制 / 自己编排 | 连上 → `workbench.start` → 讲清网页里能做什么，然后交给他 |
| **C. 导入已有脚本看看** | 查看或改一份已有脚本 | 先问脚本路径 → 连上 → `workbench.start` → `script.open` |
| **D. 只要一份清单** | 了解界面上有什么 | 连上 → `list_targets` + 逐层 `snapshot` → 报告控件清单，**不写脚本** |

选 A 时**必须再问一句"你想测哪个功能？"** —— 他要说出具体场景（登录、发消息、导出……），
你才知道该读界面哪一块、断言该验什么。他说不清就举几个例子引导，**别自己挑一个区域开干**。

**这一步没做完，不许连软件、不许拉起软件。** 拉起软件会在他桌面上开一个窗口，是副作用；
在他表态之前做，等于替他决定了要测什么。话术见 `reference/talk-scripts.md` 开场章节。

#### 1c. 探测（他选定路径之后）

**探测优先于问路径** —— 探测零成本，问用户有成本：

```
launch-target { "name": "<软件名>" }
```

它会按平台到默认安装位置探测：

- **成功** → 拿到真实端口，直接进 1e，**不必再问用户要路径**。
- **失败（找不到软件 / 平台不支持 / 名字不在清单里）** → 才进 1d 问用户。

**测网页时**用 `name: "chrome"`，流程和测桌面软件完全一样（同一套脚本、执行器、工作台，因为底层协议是通用的）。两个额外限制，**都要提前跟他说清楚**：

1. **平台不会替用户打开网页** —— 要他自己开好页面再连。
2. **软件必须处在"没在运行"的状态才能拉起。** 这是 Chromium 内核应用的单实例锁：
   已经在跑的实例会接管这次启动，新进程立刻退出，调试端口永远不会开。
   测网页时这条几乎必踩 —— 用户的浏览器十有八九正开着。
   拉起失败时工具会明说"软件已经在运行，它接管了这次启动"，
   这时候**直接照着提示转告用户**，让他完全退出软件再重试
   （Windows 注意系统托盘，关窗口不算退出）。
   **不要**自作主张替他杀进程 —— 他浏览器里有正在看的页面。

**别把探测提到 1b 之前。** 常见误解是"先探测能防幻觉"，于是抢在提问之前把软件拉起来。
防幻觉靠的是**不许陈述没验过的状态**（铁律 A），不是靠先斩后奏地连上去。

#### 1d. 用 AskUserQuestion 问路径（探测失败时才问）

**两个选项摆给用户**，让他选，不要替他决定：

- **我帮你启动** —— 需要可执行文件完整路径。macOS 要 `XXX.app/Contents/MacOS/` 里的二进制（`.app` 是文件夹，传它启动不了）；Windows 要 `.exe`；Linux 要可执行文件路径或命令名。怎么引导用户找路径，见 `reference/talk-scripts.md`。
- **软件已经开着** —— 需要他告知调试端口。他若不知道，说明得带 `--remote-debugging-port=<端口>` 重启，端口让他自己定一个（如 9222）。

**不要猜测路径去试。** 探测失败就老实问，编一个 plausible 的路径只会浪费一轮。

#### 1e. 连上

```
// 探测成功 → 用 launch-target 返回的真实端口
app.connect { "port": <launch-target 返回的端口> }

// 用户给了路径 → 平台自动拉起并开调试端口
app.connect { "port": <端口>, "appPath": "<用户给的可执行文件路径>" }

// 用户已启动软件并告知端口 → 直接连
app.connect { "port": <用户给的端口> }
```

**`appPath` 是通用路径，不是退而求其次。** 预置清单只覆盖各平台的默认安装位置，软件装在别处时走 `appPath` 是正常路径。

**连上之后才算"就绪"。** 在这之前，不许对用户说软件已启动、已连接、窗口标题是什么。

**端口只用实际值。** 端口被占用时会自动 +1，猜默认值会连错。**连接失败怎么修，见 `reference/troubleshooting.md`。**

**连上之前不许说"已就绪"。** `app.connect` 返回成功，才是你唯一能说"连上了"的时刻。

#### 1f. 连上之后：告诉他现在能做什么（**不可省略**）

只说一句"连上了"然后自己往下干，是最常见的失礼 —— 用户不知道你要带他去哪，
也不知道自己其实还有别的选择。这就是"连上了。接下来要看聊天界面有哪些控件"这类翻车的根源：
你在替他决定下一步，而他连自己能选什么都不知道。

**连上之后的第一段话**必须包含三件事：

1. **结果** —— "已经连上你的 CodeBuddy 了"（不要贴返回的 JSON）
2. **你接着要做什么** —— "我现在去读它界面上的控件，看看发消息这一步怎么点"
3. **他还能怎么选** —— 其余路径各提一句，他随时可以改主意

用户已经选了路径，所以第 2 点是确认而不是重新问；但第 3 点不能省，
因为很多人是在看到"原来还能自己录制"之后才改主意的。

**路径 B / C（他自己用网页）时，这里还要多说一件事：视觉判断的门槛。** 见下面
「视觉模型：必须提前告知」—— 他自己在网页里加的步骤，跑不通时你不在场，只能靠提前说清楚。

话术见 `reference/talk-scripts.md`。

### 第 2 步：找到控件在哪一层（**仅路径 A / D**）

Electron 软件常把不同区域做成独立嵌入层，你要点的按钮很可能**不在主窗口**。所以：

```
app.list_targets                          // 列出所有层，拿到每层 id
page.snapshot { "targetId": "<某层 id>" } // 看这一层有哪些可交互元素
```

**逐层快照直到找到目标控件**。只看主窗口会漏掉嵌入层，导致步骤点空。

从快照认控件看 `role`（是什么控件）和 `name`（叫什么）。

### 第 3 步：写出 Script JSON

```json
{
  "app": { "name": "CodeBuddy" },
  "steps": [
    { "id": "s1", "type": "fill", "source": "agent", "target": "<第2步拿到的层 id>",
      "locator": { "role": "textbox", "name": "消息" },
      "params": { "value": "你好" } },
    { "id": "s2", "type": "click", "source": "agent", "target": "<同一 id>",
      "locator": { "role": "button", "name": "发送" } },
    { "id": "s3", "type": "waitUntil", "source": "agent", "target": "<同一 id>",
      "params": { "timeoutMs": 5000,
        "assertion": { "kind": "textContains", "value": "<发送后预期出现的独特文字>" } } }
  ]
}
```

**每步都要 `target`**（第 2 步的层 id）和 **`id`**（定位失败步骤、从某步续跑用）。

**断言写什么，问用户**："操作之后，界面上会新出现什么内容？" —— 这是断言的唯一可靠来源，不要自己编。

**写完不等于能用。** 你生成的步骤是推断出来的，必须走「Agent 生成的脚本：必须自证可用」那一节的闭环（自检 → 导入 → 实跑 → 迭代）。没实跑过不许说可用。

### 第 4 步：先落盘，再决定怎么跑

**顺序不能乱**：先存文件（保证不丢），再看要不要开网页，最后才执行。

**4a. 存盘（必做）** —— 路径必须是第 1 步问来的：

```
script.export { "script": <Script 对象> }   →  { json: "..." }
```

把 `json` 写进用户指定的路径。

**4b. 二选一，问用户**：

| 目的 | 用什么 |
|---|---|
| 让用户在网页里看脚本、看每步高亮截图、自己点运行或自己录制 | `workbench.start` → `script.open` |
| 你直接执行、拿结果 | `actions.execute_steps` |

**开网页时**：`workbench.start` 会返回实际 URL —— **这个 URL 才是你给用户的地址**。不要自己拼地址（默认端口可能被占用而自动顺延，拼出来就是死链）。

**执行前必须征得用户同意**。执行是真操作（会真发消息、真点提交），提醒他先保存软件里未保存的内容。

失败时返回 `failedStepId`，改那一步再用 `fromStepId` 续跑，不必重头。

### 第 5 步：报告结果

- 跑通了 → 说哪几步过了、断言验到了什么、脚本存在哪。
- 失败了 → 说卡在第几步、界面上实际是什么、你打算怎么改。**不要把工具报错原文贴给用户**，翻成人话。

## 写好脚本的三条铁律

### 铁律 1：断言必须验证"新结果"

最容易犯也最致命的错 —— 断言恒真，测试永远通过但什么也没验证。

| 无效 ❌ | 为什么 | 有效 ✅ |
|---|---|---|
| 填了"你好" → 断言"页面出现你好" | 字是你刚打进去的，必然存在 | 点发送后 → 断言"出现对方的回复" |
| 点开菜单 → 断言"菜单项存在" | 菜单项本来就在 | 断言"子面板展开且含某选项" |

**检验方法**：把这断言单独放在操作之前，如果也能通过 —— 它就是恒真的，无效。

### 铁律 2：等条件，不等时长

`waitUntil`（等条件成立，超时算失败）是主要手段；`wait`（固定等 N 毫秒）只在确实需要空等时用，它不验证任何东西。

**超时了别急着加时间。** `waitUntil` 失败时会告诉你「最后一次未匹配原因」—— 期望什么、页面上当前实际是什么。**先看这段再决定**：

- 目标还没渲染出来 → 调大 `timeoutMs`
- 找错了地方 / 取值来源不对 → 改断言

一超时就盲目加大超时值，只会让真正的问题藏得更久。

### 铁律 3：用语义定位，不用位置定位

```json
{ "role": "button", "name": "发送" }   ✅ 改版也不容易断
{ "css": ".btn:nth-of-type(3)" }        ❌ 界面一调整就失效
```

## Agent 生成的脚本：必须自证可用（写脚本的 SOP）

这一节只针对**你（Agent）生成的脚本**，不适用于用户录制的脚本。

### 为什么单独立这一节

录制的步骤来自真实发生过的操作 —— 用户手点了那个按钮，按钮就在那儿，步骤天然可执行。

**你生成的步骤是推断出来的。** 你凭快照里看到的 role / name 猜这个元素点得到、猜这一步之后会出现什么。猜错是常态，第一次就跑通才是例外。

所以你生成脚本不是"写完交付"，而是**"写完开始验"**。跟写代码一样：定了规则要跑测试，模拟运行，失败就改，迭代到真实可用为止。**没跑过的脚本不许说可用。**

### 闭环：写 → 自检 → 导入 → 实跑 → 迭代

```
① 写        按三条铁律写出 Script JSON
② 静态自检  自己过一遍下面的检查清单
③ 导入校验  script.import   ← 非法步骤类型在这一步就会被拒（第一道闸）
④ 真实回放  actions.execute_steps   ← 必须真的跑一次
⑤ 迭代      failedStepId → 改那一步 → fromStepId 续跑，回到 ④
```

**③④⑤ 是不可跳的三步。** 只做 ①② 就把脚本交出去，等于把没编译过的代码说成能跑。

### ② 静态自检清单（实跑之前先自己过一遍）

| 检查项 | 不通过的样子 |
|---|---|
| 每个 `type` 都在合法集合内 | 写了 `press` / `type` / `dblclick` —— **这些是 Playwright 的方法名，本平台没有** |
| 每个 `locator` 都来自真实快照 | role / name 是你凭印象编的，快照里没有 |
| 每个断言都验证"新结果" | 断言恒真（见铁律 1） |
| 每步都有 `target` 和 `id` | 缺 `target` 会打到默认层，缺 `id` 定位不到失败步骤 |
| 等待用 `waitUntil` 而不是 `wait` | 用固定等待掩盖时序问题（见铁律 2） |

**步骤类型是封闭集合**（`click` / `fill` / `select` / `wait` / `assert` / `hover` / `eval` / `snapshot` / `waitUntil` / `repeat`），不在列表内的一律拒绝。完整写法见 `reference/script-json.md`。

这是本平台自有的格式，**不是 Playwright API**。写 `press` 这类 Playwright 方法名是最常见的错 —— 你脑子里的 Playwright 训练数据在这里不适用。

### ④ 真实回放是唯一判据

`script.import` 通过**只说明格式合法，不说明脚本能跑**。格式合法但 locator 点空、断言恒真、时序不够，导入全都不会报错。

只有 `actions.execute_steps` 全绿，才能说这个脚本可用。

执行前必须征得用户同意（真操作，会真发消息、真点提交），提醒他先保存软件里未保存的内容。

### ⑤ 迭代有上限

失败时返回 `failedStepId`。改那一步，用 `fromStepId` 续跑，不必从头。

**最多迭代 3 轮。** 3 轮还跑不通就停下来，把实际情况告诉用户，问他是不是流程理解错了 —— 继续盲目重试只是在猜，不是在验。

### 交付时怎么说

| 情况 | 该说 |
|---|---|
| 实跑全绿 | "跑通了，X 步全过，断言验到了……，脚本存在……" |
| 只生成没跑 | "脚本已生成存在……，**还没实跑验证**，你要我现在跑一遍吗？" |
| 跑了但失败 | "卡在第 N 步，界面上实际是……，我打算改成……" |

第二行是关键：**"生成了"和"能用"是两件事，不要混着说。**

## 什么时候才用视觉断言

有一种断言是把界面截图交给视觉模型看一眼，让它判断"是不是出现了绿色对勾""布局是不是错乱了"。**它是最后手段，不是首选。**

### 默认不用：语义断言优先

能用文字和控件属性判定的，**一律用 `textContains` / `exists` / `visible`**。视觉断言三条硬伤：

| | 语义断言 | 视觉断言 |
|---|---|---|
| 速度 | 毫秒级 | 每次要等模型，几秒到十几秒 |
| 花费 | 无 | 每次调用要花钱 |
| 确定性 | 有就是有，没有就是没有 | 同一张图未必每次给同一结论 |

**判定流程**：要验证的东西 → 快照里能读到对应文字或控件吗？

- **能** → 用语义断言。到此为止，不提视觉断言。
- **不能** → 才考虑视觉断言。

### 只有这两种情况才用

1. **界面状态说不出来，只能看出来** —— 图标、配色、布局错乱、图表趋势。
2. **目标区域是画布渲染的** —— 内容是画出来的，快照读不到。

### 必须提前告知：你查不了他配没配

**没有任何工具能查询视觉模型是否已配置。** 你只有真跑到那一步、拿到"未配置"才知道。
所以**不许猜，更不许说"你已经配好了"** —— 那是铁律 A 禁止的未验证陈述。

这就带来一个必须提前说清的后果：脚本里带视觉判断的步骤，在他机器上没配视觉模型时
会**直接失败**。而路径 B / C 是**他自己在网页里构建**，那时候你不在场 ——
他只会看到一个跑不通的步骤，完全不知道为什么、也不知道该找谁。
所以这件事**必须提前讲，不能等他踩坑**。

**三个必须提的时机**：

| 时机 | 说什么 |
|---|---|
| **1f 交付网页时**（路径 B / C） | 有一类「看画面判断」的步骤需要自备视觉模型密钥。**没配就别加这类步骤**，改用文字能验证的断言 |
| **路径 A**，你判断语义断言不够、想用视觉断言时 | 先讲代价，再问他有没有（见下节） |
| **`script.import` 后发现脚本里已有视觉判断步骤** | 主动指出来，并确认他机器上配了没有 |

**他没配（或说"我没有"）时的标准回应**：

> 那就别用「看画面判断」的步骤 —— 加了也跑不通。
> 改用文字能验证的断言：操作之后界面上会多出什么提示？某个控件的文字会不会变？

**绝不能**：替他编一个密钥、说"先用着回头再配"、或者默默跳过那一步（静默跳过 = 造假）。

### 决定要用之后，先问用户

**不要自己默默配上**、也不要替用户决定。它要花钱、要用户提供模型密钥，这两件事都得他点头。

先讲清代价，再问他手上有没有可用的视觉模型服务 —— **不要默认他有**。用户说没有，就如实说这一步跑不了，帮他换成文字能验证的断言，**绝不能编一个密钥**。

完整话术见 `reference/talk-scripts.md`。

### 三条硬规矩

1. **密钥不进脚本。** 地址和密钥只配在用户机器的运行环境里，Script JSON 里只留那句判定问题。脚本可以放心导出、提交、分享。
2. **配不好就是失败，不是跳过。** 没配好时这一步直接判不通过并说明原因。静默跳过等于这一步永远绿但什么都没验 —— 是最危险的假象。
3. **别放进循环。** 每跑一次就调一次模型，费用会成倍放大。

### 怎么写

提示词放在断言的 `value` 里（不新增字段），写成一句**能回答"是/否"的问题**：

```json
{ "id": "s3", "type": "waitUntil", "source": "agent", "target": "<层 id>",
  "params": { "timeoutMs": 15000,
    "assertion": { "kind": "visionPrompt", "value": "界面上是否出现了成功的绿色对勾图标？" } } }
```

- `locator` 可选：给了就只截这个元素，不给截整屏。**能定位就给，范围越小判得越准。**
- `timeoutMs` 给宽一点（15000 起步），它比普通断言慢。
- 只有模型明确回答"是"才算通过；模型没返回、返回别的东西，一律算不通过。

**报告结果时分清两种失败**：「没跑成」（配置或环境问题，修好就能跑）和「判不通过」（模型真看了，认为不成立 —— 这是有效结论）。混成一句"视觉断言失败"会让用户白折腾。

## 常见坑

| 坑 | 后果 | 怎么避免 |
|---|---|---|
| 只快照主窗口 | 目标控件找不到，步骤点空 | `list_targets` 后逐层快照 |
| 猜端口或猜工作台 URL | 连错、给死链 | 只用工具返回值 |
| 对控件逐个点击当"扫描" | 真触发会发消息/删数据 | 用快照枚举，需要时再写成步骤 |
| 拿快照里的位置顺序当选择器 | 改版即断 | 用 role + name |
| 能用文字验证却用了视觉断言 | 又慢又花钱，结论还不如文本断言确定 | 先确认快照里读不到，再考虑 |
| 用户没有视觉模型还硬写视觉断言 | 这一步永远不通过，脚本交付即坏 | 先问有没有，没有就换语义断言 |
| 把密钥写进脚本文件 | 脚本要提交、要分享，密钥会泄露 | 密钥只配在环境里，不进 Script JSON |
| 未经工具确认就报告状态 | 幻觉，用户照着做会踩空 | 见铁律 A |

## 能力边界

**能测什么**：Electron 桌面软件（主要场景）；Chrome 等浏览器里的网页。两者都要求被测对象带调试端口，脚本、执行器、工作台全部共用。

**测网页时的额外限制**：平台不会替用户打开浏览器和指定网址 —— 要他自己开好页面再连。

**做不到**：扫描网络请求与快捷键；操作系统原生控件（文件框、托盘、系统菜单）；滚动、按键序列、纯画布按钮；自动修复失败脚本（你自己改 JSON 重跑）。

**网页工作台上没有**：步骤列表面板（流图是唯一主视图）、"从此处运行"按钮、"单步运行"按钮、端口输入框与连接按钮。"从某步续跑"只能走 MCP 的 `fromStepId`。工作台里的脚本只存在网页内存里，刷新会丢，要留就点「导出」。

做不到或不存在的，用户问起时**如实说**，别让他白找。
