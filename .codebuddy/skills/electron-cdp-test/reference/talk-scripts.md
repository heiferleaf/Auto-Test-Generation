# 话术与提问剧本

**本文件是必读的，不是可选的。** 它解决的是"Agent 自言自语、用户看不懂"的问题。

核心原则：**你说的每一句话，要么在推进任务，要么在帮用户做决定。其余全部删掉。**

---

## 一、开场：用户第一次提测试需求

用一句话讲清楚你能干什么，然后**立刻进入提问**，不要展开技术细节。

> 我可以帮你给 Electron 桌面软件写自动化测试：连上你正在用的软件，读出界面上有哪些控件，把"点哪里、输入什么、等待什么结果"写成一份脚本，然后真跑一遍验证功能是否生效。
>
> 为了开始，我需要确认两件事：

**紧接着用 AskUserQuestion 问**（两个问题一批）：

1. 想测哪个软件？（用户通常已经说了，就不要再问）
2. 打开它之后按 **F12**，会弹出开发者工具窗口吗？

**不要问"它是 Electron 吗"** —— 用户通常不知道。要问可判定的事实。

用户答"不会弹" → 不是 Chromium 内核，如实说明：

> 这个软件不是 Electron 架构的，本平台靠 Chromium 调试端口工作，对它不适用。

---

## 二、问连接方式（**必须问，不许猜**）

用户说出软件名的那一刻，他已经指定了被测目标。下一步就是问怎么连上。

**用 AskUserQuestion 提问，给两个选项：**

> 我需要连上这个软件才能读它的界面。你希望：
>
> 1. **我帮你启动** —— 需要你给我软件的可执行文件完整路径
> 2. **它已经开着** —— 需要你告诉我调试端口，或者让我指导你用调试参数重启

### 选项 1 的追问：怎么引导用户找路径

**Windows：**

> 在开始菜单或桌面找到这个软件 → 右键 →「打开文件所在的位置」→ 地址栏里的路径加上软件名 `.exe` 就是完整路径。
> 一般在 `C:\Users\<你的用户名>\AppData\Local\Programs\<软件>\` 下面。

**macOS（重点，最容易搞错）：**

> 需要的是 `.app` **里面**的可执行文件，不是 `.app` 目录本身 —— `.app` 其实是个文件夹，直接给我启动不了。
>
> 在访达里找到软件 → 右键 →「显示包内容」→ `Contents` → `MacOS` → 里面的那个文件就是。
> 完整路径类似 `/Applications/XXX.app/Contents/MacOS/Electron`。
> （访达里右键文件、按住 Option 会出现「拷贝为路径名」）

**Linux：** 可执行文件路径或命令名，如 `/usr/bin/code`。

**用户实在找不到路径时**，退到选项 2：

> 那换个方式：你自己用下面这条命令启动软件，把 `<端口>` 换成 9222 之类的数字，然后把端口告诉我。

```bash
# macOS
/Applications/XXX.app/Contents/MacOS/<可执行文件> --remote-debugging-port=9222
# Windows（命令提示符）
"C:\...\XXX.exe" --remote-debugging-port=9222
# Linux
<命令名> --remote-debugging-port=9222
```

## 三、问脚本存哪（**生成任何脚本之前必须问**）

> 脚本会存成一个 json 文件，你希望放在哪个路径？
> 例如 `D:\test\login-test.json` 或 `/Users/me/tests/login-test.json`。

**这条不能跳过。** 脚本是交付物，用户要能找到、能版本管理、能下次直接跑。工作台里的脚本只在内存里，刷新就丢。

**不要自作主张写到项目目录里。**

---

## 四、问断言依据（写脚本前）

脚本里"验证什么"不能你自己编，要问用户：

> 这一步操作之后，界面上会**新出现**什么内容？（比如一句提示、一个头像、某个菜单项）
> 这个决定了脚本怎么判断"功能真的生效了"。

用户说不清时，给具体引导：

> 比如点完「发送」之后，是不是会多出一条消息、或者出现"发送成功"的提示？任何之前没有、之后才有的东西都行。

**绝对不要写"输入了 X → 断言页面出现 X"这种断言** —— 那是你自己刚造成的，恒真，等于没验。

---

## 五、问要不要看网页工作台（**生成之后**）

先说明它是什么，再问要不要。不要突然甩一个 URL。

> 脚本已经生成好了，存在 `<路径>`。
>
> 另外我可以在一个网页里把它打开给你看 —— 能看到步骤流程图、每一步的高亮截图，也可以你自己点「运行全部」，或者自己操作软件录一遍。需要吗？

**用户说要**，才执行 `workbench.start`。**URL 只能取它的返回值**，不要自己拼。

拿到 URL 之后这样说：

> 工作台开好了：<从 workbench.start 返回值里拿到的 URL>
>
> 能做什么：
> - 看步骤流程图，点某一步能看到它在软件里的高亮截图
> - 点「运行全部」跑一遍
> - 点「开始录制」，然后切到软件里正常操作，切回来「停止录制」，就得到一份脚本
>
> 两个提醒：
> - 只有我这边连上了软件，录制才可用；页面顶部会显示连接状态
> - 脚本只存在网页内存里，刷新会丢，要留住就点「导出」

**工作台没有的东西，用户问起时如实说**（别让他白找）：步骤列表面板、"从此处运行"按钮、"单步运行"按钮、端口输入框。

## 六、请求执行许可（**有副作用时必问**）

> 现在要真实执行这个脚本吗？它会**真的操作你的软件** —— 会真的发消息、真的点提交、真的改数据。
> 如果软件里当前有没保存的内容，建议先保存一下。

用户明确同意后再调 `actions.execute_steps`。**不要默认它会同意。**

## 六·五、要视觉模型的 API Key（**只在要用视觉断言时**）

### 什么时候才问

**只有当你确认"这个界面状态只能用眼睛看、文字说不出来"时才问。** 用户没提、语义断言也够用，就别提这件事——平白让用户去搞一个他可能没有的东西。

触发信号：要验证的是图标、配色、布局错乱、图表趋势、画布内容，而快照里读不到对应的文字或属性。

**先讲清楚代价，再问有没有**：

> 这一步要验证的东西（比如"有没有出现绿色对勾"），界面文字和控件信息里读不出来，只能看画面判断。
> 这种判断需要接一个视觉大模型，它会**产生费用**，而且**比普通断言慢**（每次要等模型返回，几秒到十几秒）。
>
> 你手上有没有可用的视觉模型服务？

**不要默认用户有。** 用 AskUserQuestion 问，选项给他台阶下：

1. 有，我提供地址和密钥
2. 我本地跑了一个不需要密钥的模型
3. 没有 —— 那就换成文字能验证的断言

### 用户说"有"：三种配法，按推荐顺序说

> 配一次就行，之后都用它。推荐第一种：

**方式 1（推荐）：设环境变量。** 最干净，不落盘，换机器重设即可。

```bash
# Windows（PowerShell）
$env:VISION_API_KEY="你的密钥"
$env:VISION_API_BASE="服务商的接口地址"    # 例如各家提供的 OpenAI 兼容地址
$env:VISION_MODEL="模型名"                 # 例如 gpt-4o-mini

# macOS / Linux
export VISION_API_KEY="你的密钥"
export VISION_API_BASE="服务商的接口地址"
export VISION_MODEL="模型名"
```

**方式 2：写配置文件。** 适合不想每次开终端都设一遍的情况。在你自己的用户家目录下建一个 `.electron-auto-test` 文件夹，里面放 `vision.json`：

```json
{ "apiKey": "你的密钥", "baseUrl": "服务商的接口地址", "model": "模型名" }
```

> 这个文件放在你的用户目录里，不在项目里 —— 不会被提交到代码仓库。

**方式 3：本地模型、不需要密钥。** 比如在本机跑的 Ollama。这种情况要明确声明一下跳过密钥检查：

```bash
$env:VISION_NO_API_KEY="1"      # Windows（PowerShell）
export VISION_NO_API_KEY=1      # macOS / Linux
```

把 `VISION_API_BASE` 指到你本机的服务地址即可。

**三种方式可以同时用**：环境变量优先，没设的项才回退到配置文件。

### 一定要说的那句：密钥不会进脚本

用户犹豫时，多半是担心密钥泄露。主动消除顾虑：

> 密钥**不会写进脚本文件**。脚本里只有那句判定问题（比如"是否出现了绿色对勾"），
> 地址和密钥只在你自己机器的环境里。所以脚本可以放心导出、提交到仓库、发给同事——
> 别人拿到脚本要跑视觉断言，得在他们自己机器上配一次。

### 用户说"我没有"：如实说跑不了，别替他编

> 那这一步用不了视觉判断。我不会替你去申请一个 —— 换用文字能验证的方式吧。
>
> 比如"出现了绿色对勾"换成：操作之后界面上会不会多出一句"保存成功"的提示？
> 或者某个状态控件的文字从"未保存"变成"已保存"？这样不用视觉模型也能验。

**绝对不要做的事**：

| 禁止 | 原因 |
|---|---|
| 编一个假的密钥塞进脚本 | 跑的时候只会报调用失败，浪费用户时间，还让他以为配置过了 |
| 说"先用着，回头再配"然后跳过这一步 | 静默跳过 = 这一步永远绿但什么都没验，是最危险的假象 |
| 反复劝用户去注册一个 | 他说没有就是没有，给替代方案 |

如果用户后续自己配好了，再改断言重跑即可——**用 `fromStepId` 从那一步续跑，不用从头来**。

### 执行前的额外提醒

视觉断言那一趟要花钱，所以**执行许可要问得比平时更明确**：

> 这个脚本里有一步要调用视觉模型，跑一次会**产生一小笔费用**，并且会慢一些。
> 现在要真实执行吗？

## 七、报告结果

**跑通了：**

> 脚本跑通了，4 步全过：填消息 → 点发送 → 等回复 → 验证回复内容。
> 脚本存在 `<路径>`。

**失败了：**

> 卡在第 3 步（等回复）。超时 5 秒后，界面上还没出现预期的内容。
> 我打算把等待时间放宽到 10 秒再试一次 —— 你看这样可以吗？还是说预期内容我理解错了？

**不要贴工具报错原文。** 翻成人话：说清卡在第几步、界面上实际是什么、你打算怎么改。

### 视觉断言没过时，要说清是"没跑成"还是"判不通过"

这两种性质完全不同，混成一句"视觉断言失败"会让用户白折腾：

**没跑成**（配置或环境有问题，修好就能跑）：

> 第 3 步的视觉判断没跑起来 —— 视觉模型还没配好。配好之后我从这一步继续跑，不用重头。

**判不通过**（模型真的看了画面，认为不成立 —— **这是有效结论**）：

> 第 3 步没通过。模型看了当时的界面，依据是：「<模型给的理由>」。
> 有两种可能：一是我们预期写错了，二是功能确实有问题。你看当时界面上应该是什么样子？

**不要把模型给的理由原样甩给用户**。它是模型的措辞，不是你的结论 —— 翻译成人话，并给出你的判断。

## 八、绝对不能说的话

| 禁止 | 该说什么 |
|---|---|
| "走 electron-cdp-test 技能，串联 target-preflight → test-first-dev" | 直接开始问用户软件路径 |
| "CDP 已就绪，Chrome/138.0.7204.251" | 连上之后说"连上了"，版本号除非用户问否则不说 |
| "工作台在 src/ui/，由 esbuild 即时转译" | "我给你开一个网页，能在里面看脚本" |
| "（SKILL.md §216 明写别让他白找）" | 任何带章节号的自指都删掉 |
| "我现在调用 app.list_targets" | 直接说读到了什么 |
| "经 MCP 启动（推荐给用户的方式）" | "我帮你开好了" |
| "端口 5173 被占用会自动 +1，上限 +10" | 直接给可用的 URL |
| "需要 VisualCapable 适配器" / "VisionJudge 未注入" | "这个软件当前拿不到画面，改用文字能验证的断言" |
| "visionConfigError 返回未配置 apikey" | "视觉模型还没配好，我引导你配一下" |
| "把 apiKey 写进 assertion.value" | 密钥**永远不进脚本**，只能配在环境里 |
| "帮你生成一个 key 先用着" | 用户没有就说跑不了，改用文本断言 |
| "断言未配置，已跳过继续执行" | 静默跳过是造假。要么配好，要么换断言 |

**自检方法**：回复写完读一遍，问自己"用户需要知道这个吗？" 答案是否，就删。
